## What to build

### Root `docker-compose.yaml`

One compose file at the repo root that brings up the entire system with `docker compose up -d --build`:

| Service | Notes |
|---|---|
| `postgres` | `postgres:17-alpine`, named volume `pgdata`, healthcheck `pg_isready`, port 5433:5432 on the host (5432 may be taken; do not collide with the Supabase stack on 54322) |
| `migrate` | one-shot: runs Codex 1's migration runner, `depends_on: postgres healthy`, `restart: "no"` |
| `seed` | one-shot after `migrate`, runs the seed importer, `restart: "no"` |
| `auth1..auth3` | build `./microservices/auth`, 3 replicas as named services (keeps the per-container log tag readable) |
| `catalog1..catalog2` | build `./microservices/catalog` |
| `streaming1..streaming2` | build `./microservices/streaming` |
| `user1..user2` | build `./microservices/user` |
| `worker1..worker2` | build `./microservices/worker`, **needs ffmpeg + ffprobe in the image**, no ports |
| `nginx` | `nginx:1.27-alpine`, publishes `8080:80`, the only backend entry point |
| `frontend` | build `./frontend`, publishes `3000:3000` |

Requirements:
- Use a YAML anchor for the repeated Go-service definition, like the existing file does.
- **Named volume `media`** mounted at `/media`: read-write in `catalog*`, `worker*` and `seed`; **read-only in `streaming*`**. That read-only mount is deliberate — streaming has no business writing.
- Every long-running service gets a healthcheck. Backends: `wget -qO- http://localhost:8080/health`.
- `depends_on` with `condition: service_healthy` so startup is ordered and `up` converges without manual steps.
- All services on one `backend` network. Only `nginx` (8080), `frontend` (3000) and `postgres` (5433) publish ports.
- Env comes from the root `.env` via `env_file` + explicit `environment:` overrides for per-service values (`CATALOG_SERVICE_URL=http://catalog1:8080` etc.).

**Service discovery caveat:** `catalog1`/`catalog2` are separate compose services, so `CATALOG_SERVICE_URL` pointing at one of them would defeat the load balancing. Put an nginx upstream in front of each service tier and point the auth proxy at that instead — i.e. `CATALOG_SERVICE_URL=http://nginx/internal/catalog` or a second lightweight nginx. Solve this cleanly and explain your choice in the report; it matters for the horizontal-scaling requirement.

### `microservices/nginx/nginx.conf`

- Keep the `lb` log format that prints `$upstream_addr` — it is how we demonstrate scaling.
- `upstream auth_service` over auth1..auth3, `least_conn`.
- Internal upstreams for catalog / streaming / user tiers.
- **Streaming needs special handling**: `proxy_buffering off` for `.ts` segments, `proxy_http_version 1.1`, pass through `Range` and `If-Range`, and do not swallow `206 Partial Content`. Raise `client_max_body_size` to 5G on the admin upload routes or video uploads will 413.
- `proxy_read_timeout` long enough for a 5 GiB upload to finish streaming through.

### Dockerfiles

- Go services: multi-stage, `golang:1.25-alpine` builder → `alpine` runtime, non-root user, `CGO_ENABLED=0`, `wget` available for the healthcheck. Model on the existing `microservices/auth/Dockerfile`.
- `worker`: same, but the runtime stage must `apk add --no-cache ffmpeg` and the image must have **both** `ffmpeg` and `ffprobe` on PATH. Verify with a build-time `RUN ffmpeg -version && ffprobe -version`.
- `frontend`: multi-stage pnpm build using Next.js **standalone** output (`output: "standalone"` in `next.config.ts`) → slim node runtime, non-root. Use `corepack`/`pnpm` with a frozen lockfile.
